# Trade socket session frames stay on the connection that logged in

## Summary

- The trade socket is built with `WebSocketClient::epoch_builder` and `channel_epoch_message_handler`, so `read_loop` knows which connection each frame came from; the session frames for an `auth` answer go out with `send_text_on_connection` bound to that answer's connection, and are dropped with a log line when that connection is gone
- The trade `auth` that `start_session` sends is bound the same way: to epoch 0 in `connect()`, and to the epoch of the `RECONNECTED` notice in `read_loop`, so a stale reconnect notice cannot put a second `auth`, and a second set of session frames, on a later socket
- Proven by the check `debug.md` saved, moved into the `tests` module of `src/websocket/client.rs` with a guard that fails if the read loop was not held, by a second check of the same shape for a stale `RECONNECTED`, and by the reported shape (`repro/loop-a.txt`) run against the whole `exec_client` binary
- Orders sent with `QfexWebSocketClient::send` and the market data socket keep the ordinary send, as the restate confirmed; the market data socket only changes the type of its frame channel
- Three slices: the session frames with the debug check; the `auth` with its check; then the prose in `docs/STATUS.md`. The NautilusTrader external contract was updated in this box

## Risks

- `send_text_on_connection` waits through a reconnect (`wait_for_active`) before the writer refuses it, so a stale session frame or `auth` can hold `read_loop` for up to the connect timeout while the transport reconnects; frames of the new connection wait in the unbounded channel meanwhile. The epoch check before each send skips the common case; the window that is left is the time between that check and the writer
- Binding the first `auth` to epoch 0 means a socket that drops in the instant between the transport's connect and that write gives `ConnectionChanged`. If `connect()` returned that as an error, a login that used to succeed through the replay buffer would fail; `connect()` instead treats `ConnectionChanged` on the first `auth` as handed to the next connection, whose `RECONNECTED` sends its own `auth`, and `logged_in` waits for that answer as today
- A session frame that is refused or times out after its write began is not sent again on that connection: if the venue never got the `subscribe`, the private channels stay unsubscribed until the next reconnect. The ordinary send has the same outcome on a dead socket, and a dead socket reconnects; a live socket whose write timed out does too (the writer requests a reconnect), so the next `auth` brings the frames back
- Both checks hold the read loop through the subscribe gate's lock (`debug.md`, "Where the check goes"). A later change that stops `read_loop` awaiting that lock on `subscribed` frames or on `RECONNECTED` would leave the checks holding nothing; criterion 2 makes that fail loudly instead of passing
- Orders sent with `send` while the trade socket reconnects can still be replayed on the next socket before its `auth`. Same root cause, out of scope by the restate; written into the `websocket` trade client row of `docs/STATUS.md` so the issue that takes it starts from there
- Switching the market data socket to `epoch_builder` too changes only the type of its frame channel; a difference between the two builders beyond the epoch would show in the market data tests (criterion 7)

## Assumptions

- Bind with `epoch_builder` and `send_text_on_connection`, not `AuthTracker` with `reconnect_buffer_waits_for_auth`, because the tracker gates only the replay buffer: the late-answer path of the check sends on the live next socket and never enters the buffer, and gating the buffer would hold replayed orders until the next login, which is the order-state decision the restate leaves to its own issue
- The trade `auth` is bound as well as the session frames, because a stale `RECONNECTED` whose `auth` lands on a later socket makes that socket answer two logins and receive the session frames twice, which the restate's "once, only after its own `auth` succeeds" rules out
- Both sockets use `epoch_builder`, with the market data socket ignoring the epoch, because one `read_loop` serves both and a second channel type would mean a second loop; what the market data socket sends does not change
- The seam for the checks stays the subscribe gate's lock, with a guard assertion, instead of a new frame-by-frame seam in `read_loop`, because the fix does not change how `read_loop` treats `subscribed` frames or `RECONNECTED`, and a seam made only for tests would add production code that the checks then test instead of the real loop
- A frame for a connection that is gone is dropped with a `warn` log line, not returned or retried, because the next connection sends its own `auth` and session frames, which is the restate's "dropped with a log line"
- `README.md` needs no change, because it states no test count and does not mention the race
- No new issue is opened for the order path: `intake.md` already names it as its own issue to open, and that belongs to box 2
